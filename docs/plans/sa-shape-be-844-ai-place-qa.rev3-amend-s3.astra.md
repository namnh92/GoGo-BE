- **Association lifecycle.** Keep the pure INSERT-time association in the existing admission transaction: structured control or an explicit typed confirmation writes `route=place_qa`; factual questions write `qaProbe=question`; unqualified bare names and fragments write `name`/`reply`; unequivocal new ordinary commands write no marker. Every marker includes the server-authored question message reference. No extra admission statement, lock, provider call or funding change. A marker is exclusion uncertainty, not a QA route. Only enabled factual intent, validated typed QA control or exact canonical name qualification establishes QA. Ordinary dispatch/frames and a completed ordinary decision prevent later promotion. Terminal settlement removes the probe when decided; stopped/reaped undecided questions use the flag decision, and name/reply recovery uses the latest prior QA route. Interrupted bare names without QA context remain ordinary. If deadline settlement itself cannot finish, retain the provisional marker through terminal writes; readers exclude this uncertain pair without treating it as QA control or emitting a QA fact/error group. Never infer `route=place_qa` from uncertainty.
- **Flag failures and deadline.** A flag rejection or a flag read exceeding 1.5 seconds means disabled for that turn, never enabled. A producer's observed disabled value is authoritative through stop/deadline/finalization; recovery does not resample it. Without a producer observation, recovery may sample once with the same disabled default. Structured or recognized stored QA control still receives disabled/stale handling. A genuinely new question with disabled/failed flag continues the ordinary lifecycle, including ordinary timeout and error semantics. Deadline settlement has one absolute 1.5-second cleanup budget covering flag lookup, pool acquisition, UPDATE and commit together; no fresh answer allowance. Stop/ceiling cancels it immediately. The DB transaction has statement timeout and destroys its connection on abort/deadline, so a late UPDATE cannot erase the retained marker. On settlement failure the turn fails/stops normally, leaves uncertain exclusion and produces no recommendation fallback from an undecided pair.
- **Fast paths.** Before flag/latest/source/catalogue/taxonomy reads, bypass QA for unequivocal new recommendation/action/guide/injection/category requests in either flag state, unless structured fields or explicit typed confirmation take precedence. The bypass sets the ordinary decision and does not await even a failing/stalled QA flag. After flag disabled, a fresh explicit factual question also bypasses latest/source/catalogue/taxonomy reads. While enabled, fresh explicit factual questions do not need latest pending state either. Bare names, ordinals, area replies, other ambiguous fragments and structured/typed controls may need latest-state validation; they are deliberately not the unequivocal fast path. Filtered recommendation history remains active in every flag state. Test success, rejection, stall, Stop and ordinary timeout, not just successful request bytes.
- **Deployment/rollback: reader floor first.** Reject the previous “rollback to the previous build” and “older reader only over-excludes” claims. `0dd18c5e` readers are unsafe for `qaProbe`. First deploy marker-aware readers/recovery everywhere (API, runner/reaper and any recommendation worker), with new send traffic paused and existing runners drained; verify every serving instance at the floor before resuming sends on this writer. This change ships dark. Mixed traffic with a pre-floor reader is forbidden even with the feature flag off, because admission writes probes while off. Rollback is flag off plus a build retaining the marker-aware history/episode filters and recovery, never an older reader. Returning below the floor requires a separate migration/owner order; do not claim draining current markers alone makes future old writes safe. Compatibility test: new admission → legacy-style finalization preserving the probe → floor reader and subsequent model requests exclude both rows. Also demonstrate the pre-floor predicate would include the pair; that is the reason deployment is prohibited, not an accepted runtime combination.
- **Text-only confirmation.** Emit `Xác nhận <complete name> · <complete current commune/province label>` (English `Confirm …`); no code, hash, nonce or visible identifier. Structured clients keep source-bound ids. Bare ordinal/name never terminally confirms a singleton: it re-asks. Accept only the whole normalized emitted identity phrase for the latest valid singleton confirm, after re-reading the place and a complete canonical-name candidate set and checking that exactly one available branch has that name + area label. Overflow, missing area, inaccessible facts, identical labels, or a phrase for another branch must re-ask without answering. Do not truncate an identity to fit the 200-character option-text bound; when unavailable/too long, emit an ordinal that conservatively re-asks. Labels remain within 40 characters. No rendered name/area is persisted. An explicit typed confirmation with no valid latest QA source is a stale control, never a new name probe or model input. Same identity on a later confirmation still denotes the same unique place; typed text makes no claim of source-message binding. Publication and fact eligibility are checked again before answering.
- **Name protection and precedence.** Parse factual prefix/suffix and its full name span before using recommendation/action words as blockers. Inside a grammatical venue name (including `Cafe Gợi Ý Quán Ngon`, `Nhà hàng Tìm Quán Cafe` and action words), these words are identity, not commands. Actual imperative clauses at the beginning or after the name, conjunction/punctuation command clauses, assistant injection and requests for alternatives still win under §3.1. No catalogue lookup just to bypass an unequivocal ordinary request; ambiguous identity grammar stays conservative QA clarification and never guesses a branch.
