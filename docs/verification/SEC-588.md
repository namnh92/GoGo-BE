## Protection boundary

**Guaranteed by structure.** From the API, no incoming request body, cookie, `env`/IP address, or request header outside `accept`, `accept-language`, `content-length`, `content-type`, `user-agent` and `x-request-id` reaches Sentry. The integration list is built explicitly (`defaultIntegrations: false`): the SDK defaults minus every `Http`/`Http.*` integration, plus exactly one `Http` integration with `maxIncomingRequestBodySize: 'none'`. The worker sends nothing to Sentry. The only attached extra is `request_id`. The request log records only method, URL, host and remote address for a request.

**Guaranteed by pattern, and tested.** In every remaining string or object — URL, query string, exception values and their causes, breadcrumbs, logged error fields — these are replaced with `[redacted]`: values of coordinate-named keys and parameters (`lat`, `lng`, `lon`, `latitude`, `longitude`, `…Lat`, `…_lat`); whole values under `coordinates`, `bbox`, `bounds`, `viewport`, `latlng`, `ll`, `geom`, `geometry`, `point`; decimal pairs with at least three decimals on both sides separated by `,` or `%2C`, including right after an encoded `@`; Google Maps `!3d…!4d…`; WKT and EWKT geometries; Drizzle `params:` lists; PostgreSQL `Failing row contains (…)` and `Key (…)=(…)` values.

**Not guaranteed.** A single unnamed decimal in free text; pairs coarser than three decimals (about 110 m); positions under other names or in other encodings (encoded polylines, geohashes, bare EWKB hex); data attached through a Sentry API call or integration added without updating this boundary (`sentry-usage.spec.ts` fails first for SDK calls); whether DEV sets `SENTRY_DSN`.

## SDK integration merge (`@sentry/node` 10.71.0)

Read in the installed build (`node_modules/.pnpm/@sentry+node@10.71.0…/@sentry/node/build/cjs`, and `@sentry+node-core@10.71.0…/@sentry/{node-core,core}/build/cjs`):

- `@sentry/node/sdk/index.js:13` — the default list contains `http.httpIntegration()`, named `Http` (`integrations/http.js:7,31`); `:44` uses `options.defaultIntegrations ?? getDefaultIntegrations(options)`, so `false` disables the default list.
- Body capture is not a separate top-level integration: `Http` builds `nodeCore.httpServerIntegration(serverOptions)` (`http.js:15-20,28`) and runs its `setupOnce` inside its own (`http.js:38-39`). That subscribes a diagnostics channel (`node-core/integrations/http/httpServerIntegration.js:59-61`, default `maxRequestBodySize: 'medium'` at `:17`), which patches each request unless the size is `'none'` (`core/integrations/http/server-subscription.js:51,56-57`) and stores the body on the request's isolation scope (`core/integrations/http/patch-request-to-capture-body.js:58-64`).
- `node-core/sdk/index.js:137-142` passes defaults and user integrations to `getIntegrationsToSetup`. `core/integration.js:23-25` flags defaults, `:28` concatenates defaults then user integrations, and `:8-19` de-duplicates **by `name`**, keeping the user instance over a default of the same name (`:13,:16`). So in 10.71 a user `Http` replaces the default `Http`; a mutation of this PR that relied on that merge (defaults plus one `Http`) still passed the real-request test.
- `core/integration.js:64-66`: `setupOnce` runs once per integration name per process (`installedIntegrations`), so the first `Http` set up in a process decides body capture for every later client in it.

This change does not rely on the name merge. `sentryIntegrations()` takes `Sentry.getDefaultIntegrations({})`, removes every name matching `/^Http(?:$|\.)/`, and appends one `Sentry.httpIntegration({ maxIncomingRequestBodySize: 'none' })`, with `defaultIntegrations: false`. `sentry-options.spec.ts` asserts the final list: unique names, exactly one HTTP integration and it is the recorded instance created with `{ maxIncomingRequestBodySize: 'none' }`, every other SDK default present in order. `sentry-request.spec.ts` asserts the client's resolved list contains only `Http` among HTTP integrations.

## Real request

`apps/api/src/sentry-request.spec.ts` initialises Sentry with the exact options `sentry.ts` builds (integration list included, OpenTelemetry set up as in `main.ts`) and an in-memory transport, starts a Fastify server on `127.0.0.1`, and sends a real `PATCH /v1/rooms/r1/constraints?lat=…&lng=…&dryRun=1` with a JSON body carrying a marker, `originLat`/`originLng`, a Google Maps URL and a GeoJSON geometry, a `referer` with an encoded Maps URL and a cookie. The handler throws; the app's `AppExceptionFilter` answers 500 and calls `Sentry.captureException`. The envelope has no `request.data`, no body marker, no coordinate and no `referer` or cookie, and keeps method, the redacted URL and query, `content-type`, `user-agent`, `x-request-id`, `request_id` and the exception. The handler also reads the request's isolation scope: the SDK instrumented the request but stored no body.

Mutation checks:

| Mutation of `sentry.ts`                                    | Result                                                                                                    |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `maxIncomingRequestBodySize: 'medium'`                     | fails at the capture-layer assertion: `expected '{"note":"body-marker-591","originLat"…' to be undefined` |
| `'medium'` and `sanitizeRequest` removed from `beforeSend` | fails at the envelope: `expected '[[{"event_id":…' not to contain 'body-marker-591'`                      |
| restored                                                   | passes                                                                                                    |

**Keeping it.** Route every Sentry call through `apps/api/src/sentry.ts`. `sentry-usage.spec.ts` fails when a file other than `sentry.ts`, `main.ts` and the exception filter imports the SDK, or when those files make any other call. `sentry-options.spec.ts` fails if the integration list gains a second HTTP integration or one that captures bodies, or if PII, local variables or tracing are switched on. `sentry-request.spec.ts` fails if a real request's body reaches the scope or the envelope. The performance test fails on catastrophic backtracking.

## Validation

`apps/api/src/sentry.spec.ts` runs a real Sentry client with `requestDataIntegration`, `linkedErrorsIntegration` and an in-memory transport. It feeds a search URL with `bounds`, `lat` and `lng`; a `referer` carrying an encoded Maps URL; a cookie; a captured body with a Maps link, a GeoJSON geometry, a nested `location`, a CSV row and room origin fields; a console breadcrumb with a coordinate pair and nested `latitude`/`longitude`; an outgoing breadcrumb with a `viewport` query; a failed insert whose Drizzle message binds EWKT and whose cause echoes `POINT(…)` with a `Failing row` detail; and an import error quoting a CSV row, a duplicate `Key (lat, lng)` and a GeoJSON body. The serialized envelope contains none of the four coordinate strings and still carries method, the redacted URL and query, `user-agent`, `x-request-id`, `request_id`, exception types, the SQL text with placeholders, the stack, and breadcrumb URL and status.

Mutation check: with the three hooks replaced by identity functions, the same spec fails on the first coordinate assertion. `sentry-options.spec.ts`, `sentry-usage.spec.ts`, `telemetry-redaction.spec.ts` and `logger.spec.ts` cover the structural settings, the call-site guard, each pattern with false-positive guards (versions, money, UUIDs, timestamps, SQL, coarse pairs, durations), and the request log.

Not run: a real Sentry project, DEV.

## Rollback

Revert. Telemetry returns to sending positions from request bodies, headers and the unnamed shapes above; nothing is stored or migrated.
