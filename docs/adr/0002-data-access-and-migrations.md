# ADR-0002: Data access, migrations and SQL boundaries

- **Status:** Accepted
- **Date:** 2026-08-27
- **Related:** FND-001, DB-001..DB-009

## Context

PostgreSQL + PostGIS is the source of truth. SRS locks Drizzle ORM for CRUD/type-safe queries and raw parameterized SQL for geo/FTS/ranking.

## Decision

1. **Drizzle schema** lives in `libs/database/src/schema/*` grouped by domain (identity, rooms, places, plans, reviews, cms). Schema files are the single model definition; Drizzle models never cross the presentation boundary as DTOs.
2. **Migrations** generated by `drizzle-kit generate` into `migrations/`, applied by `libs/database/src/migrate.ts` (drizzle migrator). Every migration is forward-tested on a snapshot and documents its rollback path in the PR. Extensions (`postgis`, `unaccent`, `pg_trgm`) enabled in migration 0000, not manually.
3. **Raw SQL** (PostGIS distance, FTS/trigram ranking, suggestion scoring joins) lives in `infrastructure/` repositories as tagged `sql` template literals — always parameterized, never string-concatenated, each covered by an integration test.
4. **Conventions (DB-001):** snake_case identifiers; `uuid` v7-style primary keys generated app-side; `timestamptz` UTC for time; money as `bigint` minor units + `char(3)` currency; soft state via explicit `status` enums; `created_at`/`updated_at` on every table; FKs `on delete` explicit, never implicit cascade on user-generated content.

## Consequences

- Type-safety for 90% of queries; hot geo/ranking paths keep full SQL control.
- drizzle-kit owns DDL diffs; hand-written SQL migrations allowed for indexes/backfills drizzle-kit cannot express (reviewed under the same rules).

## Rollback

Drizzle repos sit behind module `infrastructure/` interfaces; swapping ORM touches infrastructure only.
